# Development: Release Workflow

## Current release line

The stable public release is **Jervis 7.3.0**. The next maintenance release is **7.3.1**, currently under hardening.

Maintenance work must stay on the current major/minor line unless a new feature release is intentionally planned. Automated maintenance may move 7.3.0 → 7.3.1, but must not silently turn 7.3 into 7.4 or 8.x.

## Release source of truth

Release descriptions are code-derived and stored at:

    docs/releases/<version>.md

The publish workflow requires the matching release document and uses it as the GitHub release body. Do not substitute generic autogenerated notes for the Added / Changed / Removed / Fixed structure.

## Native release matrix

Official native builds cover:

- Linux x64
- Linux ARM64
- Windows x64
- macOS Intel
- macOS Apple Silicon

Native CI must verify that the Rust/PyO3 acceleration module is actually bundled into frozen binaries. A native build that silently falls back to NumPy does not pass release validation.

## 7.3.x hardening gate

Before 7.4 feature work, the 7.3.x line should prove:

- public installer behavior
- startup/reboot recovery
- multi-hour soak stability
- OpenClaw failure fallback
- audio-device failure handling
- speaker/identity boundaries
- repeatable benchmark output
- no known data-loss/auth-boundary regression

## Wiki publication

`docs/wiki` is the source of truth for the GitHub Wiki. The `Sync GitHub Wiki` workflow rewrites repository-relative links for the separate Wiki repository and publishes the pages after changes land on `main`.

GitHub requires the Wiki repository to be initialized with one page before automated sync can push to it.

## Security / release hygiene

Never publish credentials, private paths, IPs, serials, voiceprints, private logs, or user-specific state. Validate release artifacts and checksums before publication.
